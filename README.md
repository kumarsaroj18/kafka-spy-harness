# Kafka Spy Manual Test Harness

An end-to-end test harness that validates **specmatic kafka-spy**'s ability to infer JSON schemas from live Kafka traffic.

```
Producer (REST API) ──► Kafka ──► Consumer (real app)
                          │
                     kafka-spy (×3 topics)
                          │
                    inferred schemas
                          │
              validate vs ground-truth schemas
                          │
                   reports/report.html
```

Event payloads are generated by **Claude Code** (no API key required — Claude is the skill executor). Nine event types across three topics are published, kafka-spy infers their schemas, and a validator compares them against the ground-truth schemas in `schemas/`.

## Repository Layout

This repo must sit **beside** the `specmatic` repo, not inside it:

```
~/workspace/
├── kafka-spy-manual-test/   ← this repo
└── specmatic/               ← specmatic source repo (provides the kafka-spy JAR)
```

If your workspace is in a different location, adjust the paths accordingly — `run-test.sh` and the `run-kafka-spy-test` skill both resolve the specmatic JAR relative to `../specmatic/`.

## Prerequisites

### 1. Docker Desktop (or Docker Engine + Compose plugin)

Kafka runs in Docker. Install from <https://www.docker.com/products/docker-desktop/>.

Verify:
```bash
docker --version        # Docker 24+ recommended
docker compose version  # Compose v2+
```

> **Note**: the project uses the `docker-compose` (v1 hyphen) command in scripts. If you only have Compose v2, either install the standalone `docker-compose` binary or create an alias:
> ```bash
> echo 'alias docker-compose="docker compose"' >> ~/.zshrc && source ~/.zshrc
> ```

---

### 2. JDK 17 or later

The producer and consumer are Spring Boot 3 / Kotlin apps that require JDK 17+.

```bash
java -version   # must show 17+
```

Install options:
- **macOS (Homebrew)**: `brew install openjdk@21`
- **SDKMAN**: `sdk install java 21-tem`
- **Adoptium**: <https://adoptium.net/>

---

### 3. Python 3.10 or later

Used only by `scripts/validate-and-report.py` (schema comparison and HTML report generation). No third-party packages required — it uses only the standard library.

```bash
python3 --version   # must show 3.10+
```

---

### 4. Claude Code

Event generation is driven by Claude Code skills (slash commands). Install the Claude Code CLI:

```bash
npm install -g @anthropic-ai/claude-code
```

Or use the Claude Code desktop app or IDE extension (VS Code / JetBrains). See <https://claude.ai/code> for all install options.

Verify it is working:
```bash
claude --version
```

> **No `ANTHROPIC_API_KEY` needed** — the skills use Claude's built-in intelligence through the Claude Code session; there is no programmatic API call.

---

### 5. Specmatic `kafka-spy` JAR

The `specmatic` sibling repo must be cloned and the shadow JAR built.

#### Clone specmatic (if not already present)

```bash
cd ~/workspace    # or wherever kafka-spy-manual-test lives
git clone https://github.com/znsio/specmatic.git
```

#### Build the kafka-spy executable JAR

```bash
cd specmatic
./gradlew :specmatic-executable:unobfuscatedShadowJar
```

This produces (path relative to the specmatic root):
```
application/build/libs/specmatic-executable-<version>-all-unobfuscated.jar
```

The test harness picks up whichever JAR matches `specmatic-executable-*-all-unobfuscated.jar` automatically.

> **Gradle 17+ note**: if the build fails due to a Gradle/JDK version mismatch, run `./gradlew wrapper --gradle-version 8.7` inside the specmatic repo first.

## One-Time Setup

After the prerequisites are in place, do these steps once before the first test run.

### 1. Clone this repo

```bash
cd ~/workspace   # same parent directory as specmatic/
git clone <this-repo-url> kafka-spy-manual-test
cd kafka-spy-manual-test
```

### 2. Build the producer and consumer (first run only)

The Gradle wrapper is included — no separate Gradle installation needed.

```bash
# Producer
cd producer && ./gradlew build && cd ..

# Consumer
cd consumer && ./gradlew build && cd ..
```

This downloads dependencies (~200 MB) and compiles the Kotlin source. Subsequent runs reuse the Gradle cache.

### 3. Pull the Docker images

```bash
docker-compose pull
```

This pre-fetches `confluentinc/cp-zookeeper:7.6.0` and `confluentinc/cp-kafka:7.6.0` so the first test run doesn't wait on image downloads.

## Running the Test

There are two equivalent workflows. Choose whichever fits your preference.

### Option A — All-in-one skill (recommended)

Open Claude Code in the project root:

```bash
cd kafka-spy-manual-test
claude
```

Then run the skill:

```
/run-kafka-spy-test 100
```

Replace `100` with however many events per event type you want (larger samples give kafka-spy more data for accurate enum detection).

Claude will:
1. Start Kafka via Docker Compose
2. Start the consumer app (port 8082)
3. Start the producer app (port 8081)
4. Generate and publish 100 events × 9 event types to Kafka
5. Run kafka-spy against all three topics
6. Run the schema validator and generate `reports/report.html`
7. Show consumer received-counts
8. Stop the apps and Kafka
9. Open the HTML report in your browser

---

### Option B — Shell script + skill

This workflow uses the shell script for infrastructure (steps 1-3 and 5-7) and the Claude Code skill for event generation (step 4). Useful if you want to inspect the running services in between.

**Terminal 1** — start infrastructure:
```bash
cd kafka-spy-manual-test
./run-test.sh 100
```

The script starts Kafka, the consumer, and the producer, then **pauses** and prints:

```
[4/7] EVENT GENERATION — run this in Claude Code:
       /generate-events 100
Press Enter once the skill has finished publishing events...
```

**Claude Code** — generate events (in a new Claude Code session or the IDE extension):
```
/generate-events 100
```

Watch Claude publish all 9 × 100 events, then return to **Terminal 1** and press **Enter**.

The script continues with kafka-spy, validation, and cleanup.

## What the Harness Does — Step by Step

| Step | What happens |
|------|-------------|
| **1 – Kafka** | `docker-compose up -d` starts ZooKeeper (port 2181) and Kafka (port 9092). Waits 12 s for the broker to initialise. |
| **2 – Consumer** | `consumer/gradlew bootRun` starts the Spring Boot consumer on port 8082. It joins consumer group `main-consumer-group` and listens on all three topics. Readiness is polled via `GET /api/status`. |
| **3 – Producer** | `producer/gradlew bootRun` starts the Spring Boot producer on port 8081. It exposes `POST /api/events/bulk`. Readiness is polled via `GET /actuator/health`. |
| **4 – Generate events** | Claude generates realistic, varied JSON payloads for each event type in batches of ≤50 and POSTs them to `POST /api/events/bulk`. The producer routes each payload to the correct Kafka topic based on `eventType`. |
| **5 – kafka-spy** | Run once per topic (`order-events`, `payment-events`, `user-events`) with `--offset beginning` so it re-reads all published messages. It uses a unique consumer group ID separate from the real consumer. Inferred schemas are written to `inferred-schemas/{topic}/{EVENT_TYPE}.json`. |
| **6 – Validate** | `scripts/validate-and-report.py` compares each inferred schema against the ground-truth schema in `schemas/`. Findings are written to `reports/report.html`. The script exits with code 1 if any FAIL is present (CI-compatible). |
| **7 – Stats** | `GET /api/status` on the consumer shows how many messages each listener received. |
| **Cleanup** | Consumer and producer processes are stopped; `docker-compose down` tears down Kafka. |

## Topics and Event Types

| Topic | Event Types | Discriminator field |
|-------|-------------|---------------------|
| `order-events` | `ORDER_CREATED`, `ORDER_SHIPPED`, `ORDER_CANCELLED` | `eventType` |
| `payment-events` | `PAYMENT_INITIATED`, `PAYMENT_COMPLETED`, `PAYMENT_FAILED` | `eventType` |
| `user-events` | `USER_REGISTERED`, `USER_UPDATED`, `USER_DELETED` | `eventType` |

kafka-spy uses `--discriminator eventType` to split messages within a topic into per-event-type schemas.

## Reading the HTML Report

Open `reports/report.html` in any browser. It contains:

### Summary stats
Three stat cards showing how many event types were **PASS**, **WARNING**, or **FAIL**.

### Summary table
One row per event type with its topic, status badge, and finding count.

### Per-event-type details
For each event type:
- **Findings** — colour-coded list (red = FAIL, yellow = WARNING, green = no issues)
- **Side-by-side schema diff** — ground-truth schema (left) vs kafka-spy inferred schema (right)

### Severity levels

| Severity | Meaning |
|----------|---------|
| **FAIL** | kafka-spy produced no schema file for this event type, a required field is missing from the inferred schema, or a property type is wrong. The script exits with code 1. |
| **WARNING** | A known enum value is absent from the inferred enum (likely needs a larger sample), a ground-truth property is absent from the inferred schema, or the inferred schema contains an unexpected extra property. |
| **PASS** | All required fields are present and correctly typed, all enum values detected, no unexpected properties. |

> **Tip**: if you see WARNING on enum completeness, re-run with a larger sample size (e.g. `300` or `500`). kafka-spy can only detect enum values it has actually observed.

## Event Cache

To avoid regenerating events on every run (which is slow and token-expensive), both skills
cache generated events to disk and reuse them on subsequent runs.

### Cache location

```
events-cache/
├── ORDER_CREATED.json
├── ORDER_SHIPPED.json
├── ORDER_CANCELLED.json
├── PAYMENT_INITIATED.json
├── PAYMENT_COMPLETED.json
├── PAYMENT_FAILED.json
├── USER_REGISTERED.json
├── USER_UPDATED.json
└── USER_DELETED.json
```

Each file is a JSON array of event objects for that type.

### Cache behaviour

| Situation | What happens |
|-----------|-------------|
| File absent | Events are generated, saved to cache, then published |
| File has ≥ N events (N = requested sample-size) | First N events are taken from cache and published — **no generation** |
| File has < N events | Claude pauses and asks: **[A] Append** the missing events to the cache, or **[B] Recreate** the file entirely |
| `--fresh` flag present | Cache file is deleted and fresh events are generated, saved, and published |

### `--fresh` flag

Pass `--fresh` to either skill to force a full regeneration of all 9 cache files:

```
/generate-events 500 --fresh
/run-kafka-spy-test 500 --fresh
```

Use this when you want entirely new UUIDs, timestamps, or data variety — for example, before a
demo or after changing an event schema.

## Running Individual Skills

Both skills can be invoked independently at any point during development.

### `/generate-events [sample-size] [producer-url] [--fresh]`

Generates (or loads cached) events and publishes them without running the full test pipeline.
Requires the producer to already be running.

```
/generate-events 50
/generate-events 200 http://localhost:8081
/generate-events 500 --fresh          # discard cache, regenerate everything
```

### `/run-kafka-spy-test [sample-size] [--fresh]`

Full end-to-end orchestration — starts everything, runs the test, cleans up. This is the primary
entry point for a complete test cycle.

```
/run-kafka-spy-test
/run-kafka-spy-test 200
/run-kafka-spy-test 500 --fresh       # discard cache, regenerate everything
```

## Event Generation and Publishing Scripts

The skills delegate all event generation and publishing to two Python scripts in `scripts/`.
You can also invoke them directly from the terminal without going through a skill.

### `scripts/generate_events.py`

Generates events for **one** event type and writes them to the cache. Supports appending
to an existing cache file when you only need the missing events.

```
python3 scripts/generate_events.py <EVENT_TYPE> <count> <cache_dir> [--append]
```

| Argument | Description |
|----------|-------------|
| `EVENT_TYPE` | One of the 9 supported types (e.g. `ORDER_CREATED`) |
| `count` | Number of events to generate |
| `cache_dir` | Directory for cache files (e.g. `./events-cache`) |
| `--append` | Append to the existing file instead of overwriting |

```bash
# Create (or overwrite) a cache file with 500 ORDER_CREATED events
python3 scripts/generate_events.py ORDER_CREATED 500 ./events-cache

# Top up an existing PAYMENT_FAILED cache file with 200 more events
python3 scripts/generate_events.py PAYMENT_FAILED 200 ./events-cache --append
```

### `scripts/publish_events.py`

Reads the first `<sample_size>` events from all 9 cache files and POSTs them to the producer
in interleaved round-robin batches of ≤ 50 per topic group.

```
python3 scripts/publish_events.py <sample_size> <cache_dir> [producer_url]
```

| Argument | Description |
|----------|-------------|
| `sample_size` | Events per event type to publish |
| `cache_dir` | Directory containing cache files |
| `producer_url` | Producer base URL (default: `http://localhost:8081`) |

```bash
# Publish 100 events per type using defaults
python3 scripts/publish_events.py 100 ./events-cache

# Publish 500 events per type to a custom producer URL
python3 scripts/publish_events.py 500 ./events-cache http://localhost:8081
```

The script exits with code 1 if any cache file is missing, has fewer events than requested,
or a POST to the producer fails.

## Troubleshooting

### `./gradlew: Permission denied`
The wrapper scripts need to be executable:
```bash
chmod +x producer/gradlew consumer/gradlew
```

### Producer/consumer fails to start — "Connection refused to localhost:9092"
Kafka may not have finished initialising. The shell script waits 12 seconds after `docker-compose up -d`, but on slower machines this may not be enough. Increase the sleep in `run-test.sh` or wait and retry manually.

### `specmatic-executable-*-all-unobfuscated.jar: No such file`
The specmatic shadow JAR has not been built yet. From the `specmatic/` sibling directory:
```bash
./gradlew :specmatic-executable:unobfuscatedShadowJar
```

### kafka-spy produces empty `inferred-schemas/` directory
- Verify the producer published to Kafka: `GET http://localhost:8081/actuator/health` and check `curl -s http://localhost:8082/api/status | python3 -m json.tool`
- Ensure kafka-spy is using `--offset beginning` (it is in both the skill and the shell script) so it re-reads from the start of each partition
- Check that the topics exist: `docker exec -it <kafka-container-id> kafka-topics --bootstrap-server localhost:9092 --list`

### Report shows FAIL — "kafka-spy produced no schema file for this event type"
kafka-spy groups messages by `eventType` but needs at least one message for that type to produce a schema. Re-run `/generate-events` to ensure all 9 types were actually published.

### Report shows WARNING — "missing enum values"
kafka-spy only detects enum values it has observed. Run with a larger sample size:
```
/run-kafka-spy-test 300
```

### Port already in use (8081 or 8082)
A previous run's process may still be running:
```bash
lsof -ti :8081 | xargs kill -9 2>/dev/null
lsof -ti :8082 | xargs kill -9 2>/dev/null
```

### Kafka port 9092 already in use
A previous Docker container may still be running:
```bash
docker-compose down
docker ps   # verify no kafka/zookeeper containers remain
```
