# Kafka Spy Manual Test Harness

An end-to-end test harness that validates **specmatic kafka-spy**'s ability to infer JSON schemas from live Kafka traffic — including auto-discriminator inference — and then generates **AsyncAPI 3.0 specifications** from those schemas.

```
Producer (REST API) ──► Kafka ──► Consumer (real app)
                          │
               kafka-spy (×13 topics)
                 ├── explicit discriminator (3 original topics)
                 ├── auto-inference (3 original topics)
                 └── auto-inference (7 edge-case topics)
                          │
               inferred schemas + metadata.json
          (inferred-schemas/ and inferred-schemas-edge/)
                          │
          kafka-asyncapi-merged (original + edge, separately)
                          │
   asyncapi-specs/all-kafka-events.yaml        (6 original topics)
   asyncapi-specs-edge/all-kafka-events.yaml   (7 edge-case topics)
                          │
          validate vs ground-truth schemas
                          │
               reports/report.html
```

Event payloads are generated by **Claude Code** (no API key required — Claude is the skill executor). 25 event types across 13 topics are published, kafka-spy infers their schemas, `kafka-asyncapi-merged` generates combined AsyncAPI 3.0 YAML specs, and a validator compares the inferred schemas against the ground-truth schemas in `schemas/`.

The **edge-case topics** (EC1–EC7) deliberately stress-test specific discriminator-inference scenarios: competing candidates, false positives, partial-presence fields, overlapping value distributions, and small sample sizes.

Kafka runs in Docker. Install from <https://www.docker.com/products/docker-desktop/>.

Verify:
```bash
docker --version        # Docker 24+ recommended
docker compose version  # Compose v2+
```

> **Note**: the project uses the `docker-compose` (v1 hyphen) command in scripts. If you only have Compose v2, either install the standalone `docker-compose` binary or create an alias:

> ```

## One-Time Setup

After the prerequisites are in place, do these steps once before the first test run.

### 1. Clone this repo

```bash
cd ~/workspace   # same parent directory as specmatic/
git clone <this-repo-url> kafka-spy-manual-test
cd kafka-spy-manual-test
```

### 2. Build the producer and consumer (first run only)

The Gradle wrapper is included — no separate Gradle installation needed.

```bash
# Producer
cd producer && ./gradlew build && cd ..

# Consumer
cd consumer && ./gradlew build && cd ..
```

This downloads dependencies (~200 MB) and compiles the Kotlin source. Subsequent runs reuse the Gradle cache.

### 3. Pull the Docker images

```bash
docker-compose pull
```

This pre-fetches `confluentinc/cp-zookeeper:7.6.0` and `confluentinc/cp-kafka:7.6.0` so the first test run doesn't wait on image downloads.

## Running the Test

Open Claude Code in the project root:

```bash
cd kafka-spy-manual-test
claude
```

Then run the skill:

```
/run-kafka-spy-test 100
```

Replace `100` with however many events per event type you want (larger samples give kafka-spy more data for accurate enum detection and reliable discriminator inference).

Add `--report` to also run the JSON schema validator and open the HTML report:

```
/run-kafka-spy-test 100 --report
```

Claude will:
1. Start Kafka via Docker Compose
2. Start the consumer app (port 8082)
3. Start the producer app (port 8081)
4. Generate and publish events for all **25 event types** (2,500 events total at sample-size=100) across all 13 topics
5. Run kafka-spy ×6 on original topics (3 with explicit discriminator, 3 with auto-inference) → writes `inferred-schemas/`
6. Run auto-discovery smoke test → writes `auto-discovered-schemas/`, prints PASS/FAIL
7. Validate `metadata.json` for all 6 original topics → prints PASS/FAIL per topic
8. Run kafka-spy ×7 on edge-case topics (all with auto-inference) → writes `inferred-schemas-edge/`
9. Validate `metadata.json` for 7 edge topics (5 confirm-class checked, 2 negotiate-class WARN-skipped)
10. Run `kafka-asyncapi-merged` for original 6 topics → writes `asyncapi-specs/all-kafka-events.yaml`
11. Validate the original merged AsyncAPI spec
12. Run `kafka-asyncapi-merged` for edge 7 topics → writes `asyncapi-specs-edge/all-kafka-events.yaml`
13. Validate the edge merged AsyncAPI spec
14. _(only with `--report`)_ Run the JSON schema validator and generate `reports/report.html`
15. Show consumer received-counts for all original topics
16. Stop the apps and Kafka
17. _(only with `--report`)_ Open the HTML report in your browser

## What the Harness Does — Step by Step

| Step | What happens |
|------|-------------|
| **1 – Kafka** | `docker-compose up -d` starts ZooKeeper (port 2181) and Kafka (port 9092). Waits 12 s for the broker to initialise. |
| **2 – Consumer** | Starts on port 8082. Listens on all 6 original topics. Readiness polled via `GET /api/status`. |
| **3 – Producer** | Starts on port 8081. Exposes `POST /api/events/bulk` (discriminator-field routing) and `POST /api/events/raw?topic=` (raw topic routing). Readiness polled via `GET /actuator/health`. |
| **4 – Generate events** | Claude generates realistic varied payloads for all 25 event types (15 original + 10 edge-case). Payloads are cached in `events-cache/`. All 13 topics are published in a single `publish_events.py` call. |
| **5 – kafka-spy ×6** | Each original topic is spied separately with `--offset beginning`. The 3 original topics use `--discriminator eventType`; the 3 inference topics omit `--discriminator`. Inferred schemas and `metadata.json` are written to `inferred-schemas/{topic}/`. |
| **5b – Auto-discovery** | kafka-spy is run without `--topic` to verify auto-discovery works. Output goes to `auto-discovered-schemas/`. Pass/fail based on whether ≥13 topic directories are created (covers all 13 published topics). |
| **5c – Metadata validation (original)** | `scripts/validate-metadata.py` reads `metadata.json` from each of the 6 original topic dirs and validates result type and fields against hard-coded expectations. |
| **5d – kafka-spy ×7 edge** | Each edge topic is spied separately into `inferred-schemas-edge/`. Multi-type topics use `probe-count=60 probe-duration-ms=30000`; single-type topics use `probe-count=10 probe-duration-ms=3000`. |
| **5e – Metadata validation (edge)** | `validate-metadata.py --required-topics` checks the 5 confirm-class edge topics. The 2 negotiate-class topics (EC3-literal, EC4) are WARN-skipped pending D1 resolution. |
| **6 – kafka-asyncapi-merged (original)** | Scans `inferred-schemas/` and writes `asyncapi-specs/all-kafka-events.yaml` — a single AsyncAPI 3.0 document covering the 6 original topics. |
| **7 – AsyncAPI validate (original)** | `scripts/validate-asyncapi.py` validates the merged spec: AsyncAPI 3.0 structure, 6 channels, 6 operations, no duplicate keys, all schema files present in `components.messages`. |
| **7b – kafka-asyncapi-merged (edge)** | Scans `inferred-schemas-edge/` and writes `asyncapi-specs-edge/all-kafka-events.yaml` covering all 7 edge topics. |
| **7c – AsyncAPI validate (edge)** | Same validator with `--expected-topics 7` against the edge merged spec. |
| **8 – JSON Schema validate** | `scripts/validate-and-report.py` compares each inferred schema against ground-truth in `schemas/`. Writes `reports/report.html`. |
| **Cleanup** | Consumer and producer processes stopped; `docker-compose down` tears down Kafka. |

## Topics and Event Types

### Original 6 Topics

| Topic | Event Types | Discriminator | Auto-inferred? |
|-------|-------------|---------------|----------------|
| `order-events` | `ORDER_CREATED`, `ORDER_SHIPPED`, `ORDER_CANCELLED` | `eventType` | No — explicit flag |
| `payment-events` | `PAYMENT_INITIATED`, `PAYMENT_COMPLETED`, `PAYMENT_FAILED` | `eventType` | No — explicit flag |
| `user-events` | `USER_REGISTERED`, `USER_UPDATED`, `USER_DELETED` | `eventType` | No — explicit flag |
| `inferred-events` | `ITEM_ADDED`, `ITEM_REMOVED`, `INVENTORY_ADJUSTED` | `action` | Yes — `EXPLICIT_SINGLE` |
| `untyped-events` | _(single structure: HEARTBEAT)_ | _(none)_ | Yes — `SINGLE_TYPE` |
| `shape-events` | _(card shape: `cardNumber.json`, bank shape: `accountNumber.json`)_ | _(structural)_ | Yes — `IMPLICIT_SHAPE` |

**Note on shape-events schema filenames**: kafka-spy names schema files after the first alphabetical unique field of each structural cluster. For shape-events, the CARD_PAYMENT cluster's unique fields are `cardNumber`, `cvv`, `expiry` — first alphabetically is `cardNumber` → file is `cardNumber.json`. The BANK_TRANSFER cluster's unique fields are `accountNumber`, `bankName`, `routingNumber` → file is `accountNumber.json`. Ground-truth schemas in `schemas/shape-events/` use the same names.

### Edge-Case Topics (EC1–EC7)

These topics are designed to stress-test specific inference edge cases. All use auto-inference (no `--discriminator` flag) and write to `inferred-schemas-edge/`.

| Topic | Event Types | Expected Result | Edge Case |
|-------|-------------|-----------------|-----------|
| `competing-candidates-events` | `CC_ORDER_CREATED`, `CC_ORDER_CANCELLED` | `EXPLICIT_SINGLE eventType` | EC1 |
| `false-positive-events` | `FP_PAYMENT_INITIATED`, `FP_PAYMENT_COMPLETED` | `EXPLICIT_SINGLE eventType` | EC2 |
| `partial-field-events` | `PARTIAL_FIELD_EVENT` | `SINGLE_TYPE` | EC3-strict |
| `partial-field-literal-events` | `PARTIAL_LITERAL_EVENT` | `SINGLE_TYPE` | EC3-literal |
| `overlapping-values-events` | `OVERLAPPING_VALUE_EVENT` | `SINGLE_TYPE` | EC4 |
| `generic-events` | `GENERIC_EVENT` | `SINGLE_TYPE` | EC7 |
| `small-sample-events` | `SM_USER_REGISTERED`, `SM_USER_DELETED` | `EXPLICIT_SINGLE eventType` _(at SAMPLE_SIZE ≥ 2)_ | EC5 |

#### What each edge case tests

| EC | Scenario | Why interesting |
|----|----------|-----------------|
| **EC1** | Two fields both look like discriminator candidates: `eventType` (semantic winner) and `source` (3 rotating values, offset by 1 between types) | Tests that semantic scoring (+10 bonus for `eventType`-like names) correctly outscores a statistically similar candidate |
| **EC2** | `status` is perfectly correlated with event type (`NEW`↔initiated, `DONE`↔completed) but `eventType` is the better field | Tests that the semantic gap between `eventType` (+10) and `status` (-10) prevents a false-positive win |
| **EC3-strict** | `eventType` present in only ~60% of messages (fails the ~80% presence gate) | Tests that a partially-present field is rejected as a discriminator → `SINGLE_TYPE` |
| **EC3-literal** | Messages alternate between two structurally different shapes; neither has a consistent discriminator field | Tests that the engine merges rather than clusters when no field reliably separates shapes → `SINGLE_TYPE` (inference gap: `IMPLICIT_SHAPE` would theoretically be more accurate) |
| **EC4** | `action` field is present in 100% of messages, but `action=UPDATE` maps to two *different* payload shapes (with `name` or `amount`) | Tests that a field which doesn't cleanly separate all schemas is rejected as a discriminator → `SINGLE_TYPE` (would require composite/hierarchical discriminator to fully model) |
| **EC5** | Two event types with identical field sets; only `eventType` value differs | Tests discriminator detection at small sample sizes: SINGLE_TYPE at N=1/type (all-unique ratio), EXPLICIT_SINGLE at N≥2/type |
| **EC7** | No enum-like fields at all — only `id` (UUID), `amount` (float), `timestamp` (ISO string) | Tests that purely high-cardinality fields are never selected as discriminators → `SINGLE_TYPE` |

#### Negotiate-class topics

EC3-literal and EC4 are classified as **negotiate-class** — the engine produces `SINGLE_TYPE` (a merged schema) rather than the theoretically more informative `IMPLICIT_SHAPE`. This is arguably correct conservative behaviour (the merged schema is usable), but the information loss means these two topics are WARN-skipped in `validate-metadata.py` rather than hard-checked, pending a decision on whether the engine should be enhanced to handle these cases.

## Auto-Discriminator Inference

When kafka-spy is run **without** `--discriminator`, it executes a two-phase process:

### Phase 1 — Probe

kafka-spy collects up to `--probe-count` records per topic within `--probe-duration-ms` milliseconds. Once all topics have enough records or the duration expires, it stops collecting.

> **Pre-loaded topic tip:** For topics whose messages were all published *before* kafka-spy started, use `--probe-count 60 --probe-duration-ms 30000` for multi-type topics (long enough that the count gate is satisfied reading historical offsets) and `--probe-count 10 --probe-duration-ms 3000` for single-type topics. A short duration (e.g., 3000 ms) on multi-type topics can fire before enough messages are read to see all event types.

### Phase 2 — Inference

`DiscriminatorInferrer.infer()` is called per topic on the probe payloads. It returns one of four result types:

| Result type | Meaning | Test topic(s) |
|-------------|---------|--------------|
| `EXPLICIT_SINGLE` | A single field cleanly separates all event types | `inferred-events` (`action`), `competing-candidates-events`, `false-positive-events`, `small-sample-events` |
| `IMPLICIT_SHAPE` | No single field works but event types differ by which top-level fields are present | `shape-events` |
| `SINGLE_TYPE` | All messages share one structure, or no field cleanly separates variants | `untyped-events`, all EC3/EC4/EC7 edge topics |
| `EXPLICIT_COMPOSITE` | Two fields combined separate event types | _(not exercised in this harness)_ |

The inference result is written to `metadata.json` in the topic's output directory. `kafka-asyncapi-merged` reads this file per topic to determine discriminator handling.

### Examples

**`inferred-events`** — `action` field has 3 distinct values (`ITEM_ADDED`, `ITEM_REMOVED`, `INVENTORY_ADJUSTED`), each cleanly mapping to one structural cluster. Result: `EXPLICIT_SINGLE`, `discriminatorField: "action"`. The 3 schema files are named after the event type values with `const` on the `action` field.

**`untyped-events`** — All messages have identical structure. 1 structural cluster → `SINGLE_TYPE`. Single schema file named after the topic.

**`shape-events`** — Messages differ by which top-level fields are present. 2 structural clusters, no shared discriminator field. `deriveImplicitShape()` finds signature paths for each cluster. Result: `IMPLICIT_SHAPE`.

**`competing-candidates-events` (EC1)** — Both `eventType` and `source` are categorical, but `eventType` scores higher due to the +10 semantic bonus for `eventType`-like names. Result: `EXPLICIT_SINGLE`, `discriminatorField: "eventType"`.

**`partial-field-events` (EC3-strict)** — `eventType` is present in ~60% of messages, failing the presence gate. No other field qualifies. Result: `SINGLE_TYPE`.

**`overlapping-values-events` (EC4)** — `action` is in 100% of messages with 2 values, but `action=UPDATE` maps to two different payload shapes. Not a clean discriminator. Result: `SINGLE_TYPE`.

## AsyncAPI Spec Generation

After kafka-spy has written the inferred JSON Schema files, the skill runs `specmatic kafka-asyncapi-merged` **twice** — once for the original 6 topics and once for the 7 edge topics.

```bash
java -jar specmatic.jar kafka-asyncapi-merged \
  --config config/merged.yaml \
  --output-dir asyncapi-specs \
  inferred-schemas/

java -jar specmatic.jar kafka-asyncapi-merged \
  --config config/merged.yaml \
  --output-dir asyncapi-specs-edge \
  inferred-schemas-edge/
```

`config/merged.yaml` specifies the broker, operation type, title, version, and output filename. It has no `topic` or `discriminator` field — topics are discovered from the directory structure, and discriminators are read from per-topic `metadata.json` files automatically.

### Output

```
asyncapi-specs/
└── all-kafka-events.yaml        ← merged spec for original 6 topics

asyncapi-specs-edge/
└── all-kafka-events.yaml        ← merged spec for 7 edge-case topics
```

### Discriminator handling in the merged spec

| Topic | metadata.json result | Enum→const conversion? |
|-------|---------------------|------------------------|
| `order-events` | `EXPLICIT_SINGLE` (`eventType`) | **Yes** |
| `payment-events` | `EXPLICIT_SINGLE` (`eventType`) | **Yes** |
| `user-events` | `EXPLICIT_SINGLE` (`eventType`) | **Yes** |
| `inferred-events` | `EXPLICIT_SINGLE` (`action`) | **Yes** — `action` enum→const per message |
| `untyped-events` | `SINGLE_TYPE` | No — single schema, no discriminator |
| `shape-events` | `IMPLICIT_SHAPE` | No — structural clusters, no field discriminator |
| `competing-candidates-events` | `EXPLICIT_SINGLE` (`eventType`) | **Yes** |
| `false-positive-events` | `EXPLICIT_SINGLE` (`eventType`) | **Yes** |
| `partial-field-events` | `SINGLE_TYPE` | No |
| `partial-field-literal-events` | `SINGLE_TYPE` | No |
| `overlapping-values-events` | `SINGLE_TYPE` | No |
| `generic-events` | `SINGLE_TYPE` | No |
| `small-sample-events` | `EXPLICIT_SINGLE` (`eventType`) | **Yes** _(at SAMPLE_SIZE ≥ 2)_ |

> Per-topic config files (`config/order-events.yaml` etc.) remain in the repo for use with `specmatic kafka-asyncapi` directly if per-topic specs are needed separately.

## Reading the HTML Report

Open `reports/report.html` in any browser. It contains:

### Summary stats
Three stat cards showing how many event types were **PASS**, **WARNING**, or **FAIL**.

### Summary table
One row per event type with its topic, status badge, and finding count.

### Per-event-type details
For each event type:
- **Findings** — colour-coded list (red = FAIL, yellow = WARNING, green = no issues)
- **Side-by-side schema diff** — ground-truth schema (left) vs kafka-spy inferred schema (right)

### Severity levels

| Severity | Meaning |
|----------|---------|
| **FAIL** | kafka-spy produced no schema file for this event type, a required field is missing, or a property type is wrong. Script exits with code 1. |
| **WARNING** | A known enum value is absent from the inferred enum, a ground-truth property is absent from the inferred schema, or the inferred schema has an unexpected extra property. |
| **PASS** | All required fields present and correctly typed, all enum values detected, no unexpected properties. |

> **Tip**: if you see WARNING on enum completeness, re-run with a larger sample size (e.g. `300` or `500`). kafka-spy can only detect enum values it has actually observed.

## Event Cache

To avoid regenerating events on every run, both skills cache generated events to disk.

### Cache location

```
events-cache/
# Original 15 event types
├── ORDER_CREATED.json          ├── ITEM_ADDED.json
├── ORDER_SHIPPED.json          ├── ITEM_REMOVED.json
├── ORDER_CANCELLED.json        ├── INVENTORY_ADJUSTED.json
├── PAYMENT_INITIATED.json      ├── HEARTBEAT.json
├── PAYMENT_COMPLETED.json      ├── CARD_PAYMENT.json
├── PAYMENT_FAILED.json         └── BANK_TRANSFER.json
├── USER_REGISTERED.json
├── USER_UPDATED.json
├── USER_DELETED.json
# Edge-case event types (10 additional)
├── CC_ORDER_CREATED.json       ├── PARTIAL_LITERAL_EVENT.json
├── CC_ORDER_CANCELLED.json     ├── OVERLAPPING_VALUE_EVENT.json
├── FP_PAYMENT_INITIATED.json   ├── GENERIC_EVENT.json
├── FP_PAYMENT_COMPLETED.json   ├── SM_USER_REGISTERED.json
├── PARTIAL_FIELD_EVENT.json    └── SM_USER_DELETED.json
```

Each file is a JSON array of event objects for that type.

### Cache behaviour

| Situation | What happens |
|-----------|-------------|
| File absent | Events are generated, saved to cache, then published |
| File has ≥ N events (N = requested sample-size) | First N events are taken from cache — **no generation** |
| File has < N events | Claude pauses and asks: **[A] Append** the missing events, or **[B] Recreate** the file |
| `--fresh` flag present | Cache file is deleted and fresh events are generated |

## Troubleshooting

### `./gradlew: Permission denied`
```bash
chmod +x producer/gradlew consumer/gradlew
```

### Producer/consumer fails to start — "Connection refused to localhost:9092"
Kafka may not have finished initialising. Increase the sleep in `run-test.sh` or wait and retry manually.

### `specmatic-executable-*-all-unobfuscated.jar: No such file`
```bash
cd ../specmatic && ./gradlew :specmatic-executable:unobfuscatedShadowJar
```

### kafka-spy produces empty `inferred-schemas/` directory
- Verify the producer published to Kafka: check `curl -s http://localhost:8082/api/status | python3 -m json.tool`
- Ensure kafka-spy is using `--offset beginning`
- Check that topics exist: `docker exec -it <kafka-container-id> /usr/bin/kafka-topics --bootstrap-server localhost:9092 --list`

### shape-events produces only 1 schema file (not 2)
`IMPLICIT_SHAPE` clusters weren't detected — the two shapes don't have enough structural separation. Ensure CARD_PAYMENT events have no `routingNumber`/`accountNumber`/`bankName` fields, and BANK_TRANSFER events have no `cardNumber`/`expiry`/`cvv` fields. Also increase sample size so both shapes have ≥ 5 probe records each:
```
/run-kafka-spy-test 200
```

### inferred-events metadata.json says SINGLE_TYPE instead of EXPLICIT_SINGLE
All probe messages had the same `action` value, or fewer than 2 unique structural clusters were detected. Ensure `generate_events.py` produces all 3 action values (`ITEM_ADDED`, `ITEM_REMOVED`, `INVENTORY_ADJUSTED`) in the cache and increase `--probe-count`:
```
/run-kafka-spy-test 200 --fresh
```

### small-sample-events metadata.json says SINGLE_TYPE instead of EXPLICIT_SINGLE
This is expected when `SAMPLE_SIZE=1` (only 1 event per type = 2 messages total). With 2 messages and 2 unique `eventType` values, the ratio is 1.0 (all-unique) — the engine cannot distinguish a discriminator from a unique ID with only 1 sample per value. At `SAMPLE_SIZE ≥ 2` this resolves to `EXPLICIT_SINGLE`. If you see this unexpectedly at larger sample sizes, re-run with a fresh topic and check that messages were published in interleaved order (the skill handles this automatically).

### Auto-discovery FAIL — fewer than 13 topics discovered
With 13 topics now published, the smoke test expects at least 13 directories. If fewer are found, check that the edge-case topics were published (Step 4 of the skill publishes all 13 topics in one call). Run with `--fresh` to ensure all event caches are present:
```
/run-kafka-spy-test --fresh
```

### Edge metadata validation FAIL — a confirm-class topic is SINGLE_TYPE
For `competing-candidates-events` or `false-positive-events`, the probe didn't see enough messages to distinguish the discriminator. Check that events were published with sufficient interleaving (the skill uses `probe-count=60`). For `small-sample-events`, see the note above about `SAMPLE_SIZE ≥ 2`.

### EC3-literal / EC4 produce SINGLE_TYPE — is this a bug?
No — this is known behaviour. `partial-field-literal-events` (EC3-literal) has alternating shapes where neither shape has a consistently present discriminator field. `overlapping-values-events` (EC4) has an `action` field that maps to multiple schemas for the same value. In both cases, the engine correctly determines that no single field cleanly separates all variants and falls back to a merged `SINGLE_TYPE` schema. These two topics are intentionally WARN-skipped in metadata validation.

### AsyncAPI validation fails — "Event type X missing from components.messages"
The `inferred-schemas/{topic}/` directory does not contain a `*.json` file for that event type. Re-run with a larger sample size or check that the producer published all event types:
```bash
ls inferred-schemas/order-events/    # should show 3 *.json files + metadata.json
```

### AsyncAPI validation fails — "no property with 'const' found"
Only applies to `EXPLICIT_SINGLE` topics. The discriminator field was not inferred as a single-value enum. Re-run with a larger sample size so kafka-spy has enough data.

```bash
lsof -ti :8082 | xargs kill -9 2>/dev/null
```
