# Kafka Spy Manual Test Harness

An end-to-end test harness that validates **specmatic kafka-spy**'s ability to infer JSON schemas from live Kafka traffic — including auto-discriminator inference — and then generates **AsyncAPI 3.0 specifications** from those schemas.

```
Producer (REST API) ──► Kafka ──► Consumer (real app)
                          │
                   kafka-spy (×6 topics)
                     ├── explicit discriminator (3 topics)
                     └── auto-inference (3 topics)
                          │
               inferred schemas + metadata.json
                   (inferred-schemas/)
                          │
               kafka-asyncapi-merged (once)
                          │
         asyncapi-specs/all-kafka-events.yaml
                          │
          validate vs ground-truth schemas
                          │
               reports/report.html
```

Event payloads are generated by **Claude Code** (no API key required — Claude is the skill executor). Fifteen event types across six topics are published, kafka-spy infers their schemas (using explicit discriminator for three topics and auto-inference for three), `kafka-asyncapi-merged` generates a single combined AsyncAPI 3.0 YAML spec, and a validator compares the inferred schemas against the ground-truth schemas in `schemas/`.

```bash
docker --version        # Docker 24+ recommended
```

## One-Time Setup

After the prerequisites are in place, do these steps once before the first test run.

### 1. Clone this repo

```bash
cd ~/workspace   # same parent directory as specmatic/
git clone <this-repo-url> kafka-spy-manual-test
cd kafka-spy-manual-test
```

### 2. Build the producer and consumer (first run only)

The Gradle wrapper is included — no separate Gradle installation needed.

```bash
# Producer
cd producer && ./gradlew build && cd ..

# Consumer
cd consumer && ./gradlew build && cd ..
```

This downloads dependencies (~200 MB) and compiles the Kotlin source. Subsequent runs reuse the Gradle cache.

### 3. Pull the Docker images

```bash
docker-compose pull
```

This pre-fetches `confluentinc/cp-zookeeper:7.6.0` and `confluentinc/cp-kafka:7.6.0` so the first test run doesn't wait on image downloads.

## Running the Test

Open Claude Code in the project root:

```bash
cd kafka-spy-manual-test
claude
```

Then run the skill:

```
/run-kafka-spy-test 100
```

Replace `100` with however many events per event type you want (larger samples give kafka-spy more data for accurate enum detection and reliable discriminator inference).

Add `--report` to also run the JSON schema validator and open the HTML report:

```
/run-kafka-spy-test 100 --report
```

Claude will:
1. Start Kafka via Docker Compose
2. Start the consumer app (port 8082)
3. Start the producer app (port 8081)
4. Generate and publish events for all 15 event types (1,500 events total at sample-size=100)
5. Run kafka-spy ×6 (3 with explicit discriminator, 3 with auto-inference) → writes `inferred-schemas/`
6. Run auto-discovery smoke test → writes `auto-discovered-schemas/`, prints PASS/FAIL
7. Validate `metadata.json` for all 6 topics → prints PASS/FAIL per topic
8. Run `kafka-asyncapi-merged` once → writes `asyncapi-specs/all-kafka-events.yaml`
9. Validate the merged AsyncAPI spec
10. _(only with `--report`)_ Run the JSON schema validator and generate `reports/report.html`
11. Show consumer received-counts for all 6 topics
12. Stop the apps and Kafka
13. _(only with `--report`)_ Open the HTML report in your browser

## What the Harness Does — Step by Step

| Step | What happens |
|------|-------------|
| **1 – Kafka** | `docker-compose up -d` starts ZooKeeper (port 2181) and Kafka (port 9092). Waits 12 s for the broker to initialise. |
| **2 – Consumer** | Starts on port 8082. Listens on all 6 topics. Readiness polled via `GET /api/status`. |
| **3 – Producer** | Starts on port 8081. Exposes `POST /api/events/bulk` (discriminator-field routing) and `POST /api/events/raw?topic=` (raw topic routing). Readiness polled via `GET /actuator/health`. |
| **4 – Generate events** | Claude generates realistic varied payloads for all 15 event types. Payloads are cached in `events-cache/`. Events with an `eventType` or `action` field go to `POST /api/events/bulk`; events with no routing field (HEARTBEAT, CARD_PAYMENT, BANK_TRANSFER) go to `POST /api/events/raw?topic=`. |
| **5 – kafka-spy ×6** | Each topic is spied separately with `--offset beginning`. The 3 original topics use `--discriminator eventType`; the 3 new topics omit `--discriminator` so auto-inference runs. Inferred schemas and `metadata.json` are written to `inferred-schemas/{topic}/`. |
| **5b – Auto-discovery** | kafka-spy is run without `--topic` to verify auto-discovery works. Output goes to `auto-discovered-schemas/` (separate from `inferred-schemas/` to avoid polluting validators). Pass/fail based on whether ≥6 topic directories are created. |
| **5c – Metadata validation** | `scripts/validate-metadata.py` reads `metadata.json` from each of the 6 topic dirs and validates the result type and fields match hard-coded expectations. |
| **6 – kafka-asyncapi-merged** | `kafka-asyncapi-merged` scans all topic subdirectories in `inferred-schemas/` and writes `asyncapi-specs/all-kafka-events.yaml` — a single AsyncAPI 3.0 document covering all 6 topics. Per-topic `metadata.json` files drive discriminator handling: `EXPLICIT_SINGLE` triggers enum→const conversion on the discriminator field; all other result types emit schemas as-is. |
| **7 – AsyncAPI validate** | `scripts/validate-asyncapi.py` validates `all-kafka-events.yaml`: checks AsyncAPI 3.0 structure, 6 channels, 6 operations, no duplicate message keys, and that every inferred schema file has a corresponding entry in `components.messages`. Per-topic checks (inferred-events const values, untyped-events single schema, shape-events ≥2 clusters) are cross-referenced against `inferred-schemas/`. |
| **8 – JSON Schema validate** | `scripts/validate-and-report.py` compares each inferred schema against ground-truth in `schemas/`. Writes `reports/report.html`. |
| **Cleanup** | Consumer and producer processes stopped; `docker-compose down` tears down Kafka. |

## Topics and Event Types

| Topic | Event Types | Discriminator | Auto-inferred? |
|-------|-------------|---------------|----------------|
| `order-events` | `ORDER_CREATED`, `ORDER_SHIPPED`, `ORDER_CANCELLED` | `eventType` | No — explicit flag |
| `payment-events` | `PAYMENT_INITIATED`, `PAYMENT_COMPLETED`, `PAYMENT_FAILED` | `eventType` | No — explicit flag |
| `user-events` | `USER_REGISTERED`, `USER_UPDATED`, `USER_DELETED` | `eventType` | No — explicit flag |
| `inferred-events` | `ITEM_ADDED`, `ITEM_REMOVED`, `INVENTORY_ADJUSTED` | `action` | Yes — `ExplicitSingle` |
| `untyped-events` | _(single structure: HEARTBEAT)_ | _(none)_ | Yes — `NoVariants → SingleType` |
| `shape-events` | _(card shape: `cardNumber.json`, bank shape: `accountNumber.json`)_ | _(structural)_ | Yes — `ImplicitShape` |

**Note on shape-events schema filenames**: kafka-spy names schema files after the first alphabetical unique field of each structural cluster. For shape-events, the CARD_PAYMENT cluster's unique fields are `cardNumber`, `cvv`, `expiry` — first alphabetically is `cardNumber` → file is `cardNumber.json`. The BANK_TRANSFER cluster's unique fields are `accountNumber`, `bankName`, `routingNumber` → file is `accountNumber.json`. Ground-truth schemas in `schemas/shape-events/` use the same names.

**Note on metadata.json for explicit-discriminator topics**: when `--discriminator eventType` is passed to kafka-spy, the probe phase is skipped entirely and `inferenceResultsByTopic` is never populated. The metadata writer receives `null` and writes `{"discriminatorResultType":"SINGLE_TYPE"}`. `kafka-asyncapi-merged` reads this and emits the `eventType` field as a single-value enum rather than a `const` — see the discriminator handling table in [AsyncAPI Spec Generation](#asyncapi-spec-generation).

## Auto-Discriminator Inference

When kafka-spy is run **without** `--discriminator`, it executes a two-phase process:

### Phase 1 — Probe

kafka-spy collects up to `--probe-count` records (default 100) per topic within `--probe-duration-ms` milliseconds (default 15 000 ms). Once all topics have enough records or the duration expires, it stops collecting.

### Phase 2 — Inference

`DiscriminatorInferrer.infer()` is called per topic on the probe payloads. It returns one of five result types:

| Result type | Meaning | Test topic |
|-------------|---------|------------|
| `ExplicitSingle` | A single field cleanly separates all event types | `inferred-events` (field: `action`) |
| `ExplicitComposite` | Two fields combined separate event types | _(not exercised in this harness)_ |
| `ImplicitShape` | No single field works but event types differ by which top-level fields are present | `shape-events` |
| `NoVariants` | All messages share one structure — single event type, no discriminator needed | `untyped-events` |
| `None` | Multiple structural clusters but no field is clean enough to act as discriminator | _(not exercised)_ |

The inference result is written to `metadata.json` in the topic's output directory. `kafka-asyncapi-merged` reads this file per topic to determine discriminator handling.

### Examples

**`inferred-events`** — `action` field has 3 distinct values (`ITEM_ADDED`, `ITEM_REMOVED`, `INVENTORY_ADJUSTED`), each cleanly mapping to one structural cluster. `DiscriminatorInferrer` scores `action` highly (it is in `POSITIVE_NAMES`, all values are `STRING_TOKEN`, each value maps to exactly one cluster). Result: `ExplicitSingle`, `discriminatorField: "action"`. The 3 inferred schema files are `ITEM_ADDED.json`, `ITEM_REMOVED.json`, `INVENTORY_ADJUSTED.json` with `const` on the `action` field.

**`untyped-events`** — All messages have identical structure: `serviceId`, `timestamp`, `healthy`, `uptimeSeconds`. Structural clustering produces 1 cluster. `DiscriminatorInferrer` short-circuits and returns `NoVariants`. Result: `SINGLE_TYPE` in metadata.json. The single inferred schema file is `untyped-events.json` (named after the topic).

**`shape-events`** — Messages differ by which top-level fields are present (CARD_PAYMENT has `cardNumber`/`expiry`/`cvv`; BANK_TRANSFER has `routingNumber`/`accountNumber`/`bankName`). Structural clustering produces 2 clusters. No single field appears in both clusters with distinct values, so `ExplicitSingle` fails. `deriveImplicitShape()` finds signature paths for each cluster. Result: `ImplicitShape`. Schema files are named `cardNumber.json` and `accountNumber.json` (first alphabetical unique field per cluster).

## AsyncAPI Spec Generation

After kafka-spy has written the inferred JSON Schema files, **Step 6** runs `specmatic kafka-asyncapi-merged` once to produce a single [AsyncAPI 3.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0) YAML document covering all 6 topics.

```bash
java -jar specmatic.jar kafka-asyncapi-merged \
  --config config/merged.yaml \
  --output-dir asyncapi-specs \
  inferred-schemas/
```

`config/merged.yaml` specifies the broker, operation type, title, version, and output filename. It has no `topic` or `discriminator` field — topics are discovered from the directory structure, and discriminators are read from per-topic `metadata.json` files automatically.

### Output

```
asyncapi-specs/
└── all-kafka-events.yaml    ← single merged spec (all 6 topics)
```

The merged spec contains:
- 6 `channels` entries (one per topic, PascalCase key, `address` = raw topic name)
- 6 `operations` entries
- All event-type messages from all 6 topics in `components.messages`
- Collision-free message keys (topic name is used as a prefix when two topics share an event-type name)

### Discriminator handling in the merged spec

| Topic | metadata.json result | Enum→const conversion? |
|-------|---------------------|------------------------|
| `order-events` | `SINGLE_TYPE` | No — schemas emitted as-is |
| `payment-events` | `SINGLE_TYPE` | No — schemas emitted as-is |
| `user-events` | `SINGLE_TYPE` | No — schemas emitted as-is |
| `inferred-events` | `EXPLICIT_SINGLE` (`action`) | **Yes** — `action` enum→const per message |
| `untyped-events` | `SINGLE_TYPE` | No — single schema, no discriminator |
| `shape-events` | `IMPLICIT_SHAPE` | No — structural clusters, no field discriminator |

> **Note on SINGLE_TYPE for order/payment/user**: kafka-spy writes `SINGLE_TYPE` when `--discriminator` is passed explicitly, because the probe phase is skipped and the inference result is never computed. `kafka-asyncapi-merged` therefore reads `null` discriminator for these topics and emits the `eventType` field as a single-value `enum` array rather than a `const`. This is correct and expected behaviour for the merged spec.
>
> Per-topic config files (`config/order-events.yaml` etc.) with `discriminator: eventType` remain in the repo for use with `specmatic kafka-asyncapi` directly if per-topic specs are needed separately.

## Reading the HTML Report

Open `reports/report.html` in any browser. It contains:

### Summary stats
Three stat cards showing how many event types were **PASS**, **WARNING**, or **FAIL**.

### Summary table
One row per event type with its topic, status badge, and finding count.

### Per-event-type details
For each event type:
- **Findings** — colour-coded list (red = FAIL, yellow = WARNING, green = no issues)
- **Side-by-side schema diff** — ground-truth schema (left) vs kafka-spy inferred schema (right)

### Severity levels

| Severity | Meaning |
|----------|---------|
| **FAIL** | kafka-spy produced no schema file for this event type, a required field is missing, or a property type is wrong. Script exits with code 1. |
| **WARNING** | A known enum value is absent from the inferred enum, a ground-truth property is absent from the inferred schema, or the inferred schema has an unexpected extra property. |
| **PASS** | All required fields present and correctly typed, all enum values detected, no unexpected properties. |

> **Tip**: if you see WARNING on enum completeness, re-run with a larger sample size (e.g. `300` or `500`). kafka-spy can only detect enum values it has actually observed.

## Event Cache

To avoid regenerating events on every run, both skills cache generated events to disk.

### Cache location

```
events-cache/
├── ORDER_CREATED.json         ├── ITEM_ADDED.json
├── ORDER_SHIPPED.json         ├── ITEM_REMOVED.json
├── ORDER_CANCELLED.json       ├── INVENTORY_ADJUSTED.json
├── PAYMENT_INITIATED.json     ├── HEARTBEAT.json
├── PAYMENT_COMPLETED.json     ├── CARD_PAYMENT.json
├── PAYMENT_FAILED.json        └── BANK_TRANSFER.json
├── USER_REGISTERED.json
├── USER_UPDATED.json
└── USER_DELETED.json
```

Each file is a JSON array of event objects for that type.

### Cache behaviour

| Situation | What happens |
|-----------|-------------|
| File absent | Events are generated, saved to cache, then published |
| File has ≥ N events (N = requested sample-size) | First N events are taken from cache — **no generation** |
| File has < N events | Claude pauses and asks: **[A] Append** the missing events, or **[B] Recreate** the file |
| `--fresh` flag present | Cache file is deleted and fresh events are generated |

## Troubleshooting

### `./gradlew: Permission denied`
```bash
chmod +x producer/gradlew consumer/gradlew
```

### Producer/consumer fails to start — "Connection refused to localhost:9092"
Kafka may not have finished initialising. Increase the sleep in `run-test.sh` or wait and retry manually.

### `specmatic-executable-*-all-unobfuscated.jar: No such file`
```bash
cd ../specmatic && ./gradlew :specmatic-executable:unobfuscatedShadowJar
```

### kafka-spy produces empty `inferred-schemas/` directory
- Verify the producer published to Kafka: check `curl -s http://localhost:8082/api/status | python3 -m json.tool`
- Ensure kafka-spy is using `--offset beginning`
- Check that topics exist: `docker exec -it <kafka-container-id> kafka-topics --bootstrap-server localhost:9092 --list`

### shape-events produces only 1 schema file (not 2)
`ImplicitShape` clusters weren't detected — the two shapes don't have enough structural separation. Ensure CARD_PAYMENT events have no `routingNumber`/`accountNumber`/`bankName` fields, and BANK_TRANSFER events have no `cardNumber`/`expiry`/`cvv` fields. Also increase sample size so both shapes have ≥ 5 probe records each:
```
/run-kafka-spy-test 200
```

### inferred-events metadata.json says SINGLE_TYPE instead of EXPLICIT_SINGLE
All probe messages had the same `action` value, or fewer than 2 unique structural clusters were detected. Ensure `generate_events.py` produces all 3 action values (`ITEM_ADDED`, `ITEM_REMOVED`, `INVENTORY_ADJUSTED`) in the cache and increase `--probe-count`:
```
/run-kafka-spy-test 200 --fresh
```

### validate-metadata.py reports SINGLE_TYPE for order/payment/user-events as PASS
This is **correct and expected**. Those topics are run with explicit `--discriminator eventType`, which skips the probe phase. The metadata writer receives `null` (inference result was never populated) and writes `{"discriminatorResultType":"SINGLE_TYPE"}`. kafka-asyncapi for those topics reads the discriminator from the config YAML directly — it does not rely on metadata.json.

### AsyncAPI validation fails — "Event type X missing from components.messages"
The `inferred-schemas/{topic}/` directory does not contain a `*.json` file for that event type. Re-run with a larger sample size or check that the producer published all event types:
```bash
ls inferred-schemas/order-events/    # should show 3 *.json files + metadata.json
```

### AsyncAPI validation fails — "no property with 'const' found"
Only applies to `EXPLICIT_SINGLE` topics. The discriminator field was not inferred as a single-value enum. Re-run with a larger sample size so kafka-spy has enough data.

### validate-asyncapi.py reports PASS for untyped-events and shape-events without const
This is **correct**. The const check is skipped for `SINGLE_TYPE` and `IMPLICIT_SHAPE` topics — those result types have no discriminator field to convert. The validator instead checks structural validity and topic-specific assertions (single schema file for untyped-events, ≥2 cluster signatures for shape-events).

### Port already in use (8081 or 8082)
```bash
lsof -ti :8081 | xargs kill -9 2>/dev/null
lsof -ti :8082 | xargs kill -9 2>/dev/null
```

### Kafka port 9092 already in use
```bash
docker-compose down
docker ps   # verify no kafka/zookeeper containers remain
```
